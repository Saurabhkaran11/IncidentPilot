# Permission design

Six identities, each able to do exactly one job. Every row below is
generated by `infra/lib/incidentpilot-stack.ts` and verifiable in the
synthesized template (`cd infra && npx cdk synth`).

The rule these tables encode: **sharing a code repository is not sharing an
IAM role.** The investigator and the executor run from the same monorepo and
cannot do each other's work.

## Runtime roles

### Demo processor — `incidentpilot-demo-processor-role`

| Action | Resource | Why |
|---|---|---|
| `dynamodb:PutItem` | expected results table | The one business effect: a conditional insert keyed by request ID. |
| `dynamodb:GetItem` | expected results table | Read back the existing row after a condition failure, to tell "already completed" from "conflict". |
| `logs:CreateLogGroup`, `CreateLogStream`, `PutLogEvents` | its own log group | Its failures must be real CloudWatch evidence. |

**Deliberately absent:** any access to the quarantine results table. That
single omission is what makes the demo's `AccessDenied` an authentic AWS
authorization failure rather than a simulated one. Also absent:
`DeleteItem`, `UpdateItem`, `Scan`, `Query` — `grantReadWriteData` would
have added all four; the processor calls none of them.

### Investigation runtime — `incidentpilot-investigator-role`

| Action | Resource | Why |
|---|---|---|
| `logs:FilterLogEvents`, `GetLogEvents`, `DescribeLogStreams` | the registered log group only | `get_error_evidence`, bounded to the incident's time window. |
| `lambda:GetAlias`, `GetFunctionConfiguration`, `ListVersionsByFunction` | the registered function only | `get_release_diff` compares deployed vs known-good configuration. |
| `dynamodb:GetItem` | expected results table | `get_pending_request_summary` checks whether results exist. |
| `bedrock:InvokeModel`, `InvokeModelWithResponseStream` | the configured foundation model | The agent itself. Narrow to the exact model ID you enabled. |

**Deliberately absent:** every mutating action. This role cannot
`UpdateAlias`, cannot write to any table, cannot assume the executor role,
and has no `iam:*`. A fully compromised agent can produce a wrong
recommendation and nothing else.

### Recovery executor — `incidentpilot-executor-role`

| Action | Resource | Why |
|---|---|---|
| `lambda:UpdateAlias`, `lambda:GetAlias` | **one alias ARN** | The approved rollback, revision-preconditioned. Scoped to the single registered alias — not the function, not a wildcard. |
| `lambda:InvokeFunction` | the same alias ARN | Post-rollback canary and bounded replay. |
| `dynamodb:GetItem` | expected results table | Independent verification: read back the canary's durable result and compare its payload hash. |

**Deliberately absent:** any `iam:*` action, any second function, any
wildcard resource, and any write to the results table. The executor proves
recovery by *reading* what the application wrote — it cannot fabricate the
evidence it verifies against.

## Human and local identities

| Identity | How it authenticates | What it can do |
|---|---|---|
| Deployment owner | local AWS credentials (`cdk deploy`) | Create the demo stack; publish versions; inject the fault via CLI. Never used by the running product. |
| Authenticated operator (local live) | 30-minute hashed bearer token minted after an STS check, loopback only | Inspect incidents, start investigations, approve/reject, submit demo requests. |
| Development actor (fixture mode) | fixed actor, loopback only, no token | The same operator actions against simulated AWS. Rejected in hosted mode. |
| Public walkthrough visitor | none | Read fixed fixture data only. Cannot inject faults or execute recovery — fault injection is a CLI command with no HTTP route at all. |

## Verifying the boundaries

```bash
cd infra && npx cdk synth
```

Then confirm in `cdk.out/IncidentPilotDemo.template.json`:

- the processor's policy never mentions the quarantine table;
- the executor's policy contains no `iam:` action and its Lambda actions
  resolve to the alias, not the function;
- the investigator's policy contains no write action of any kind.

`docs/decisions/0004-separate-executor-identity.md` and
`0010-alias-rollback-not-iam-expansion.md` record why.

## Note on resource-level support

`lambda:UpdateAlias` and `lambda:InvokeFunction` support resource-level
permissions on an alias ARN, which is what makes the executor's scope
meaningful. `bedrock:InvokeModel` is scoped to a foundation-model ARN
pattern here; narrow it to the specific model you enable. Verify each
action's resource-level support against current service documentation before
copying these policies anywhere that matters — this table reflects the demo
stack, not a general-purpose IAM recommendation.
